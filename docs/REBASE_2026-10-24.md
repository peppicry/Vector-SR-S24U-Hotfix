## Is the original issue fixed upstream?

The Samsung protection is absent from both the latest tagged release and current master. Between 3136 and 3151, the complete unpatched files have identical Git blob IDs:

- `legacy/src/main/java/org/matrix/vector/legacy/LegacyDelegateImpl.java`: `885d4087855f33992d2440433cbf71f0ffe1a2dd`
- `legacy/src/main/java/de/robv/android/xposed/XposedBridge.java`: `b83883c08ab9618f67011c1ba5c83f5efe112473`

The official dispatcher still runs legacy before/after callbacks for `getApplicationInfoAsUser("android.uid.system", ...)`. An original lookup exception is stored and rethrown to the caller; it is not automatically logged merely because the original lookup failed. However, a legacy callback that throws while handling that result reaches `XposedBridge.log(Throwable)`, which logs the exact `NameNotFoundException` without the Samsung filter. That is the failure path addressed by this patch.

The current LSPlant update includes native-method signatures, Android 17 JNI IDs, CloseGuard/Knox allocation behavior and trampoline fixes. Those changes do not add the Java pseudo-package guard or logging filter. No upstream issue matching `android.uid.system` or `VectorLegacyBridge` was returned by the issue searches performed during this review; that search result is not proof that no report exists.

## Isolated Java reproduction

A local host-JVM harness compiled the actual `processLegacyHook`, `LegacyApiSupport`, `log(Throwable)` and `XC_MethodHook` source from each compared revision. Android framework classes were stubbed; `VectorLegacyCallback` state operations used an equivalent Java adapter. A synthetic after-callback called `getResultOrThrowable()`, causing it to rethrow the expected platform lookup exception.

For 1,000 exact pseudo-package lookups:

| Tested code | Original invocations | Legacy callback invocations | Error logs | Original exception propagated |
| --- | ---: | ---: | ---: | ---: |
| Official 3131 | 1,000 | 2,000 | 1,000 | 1,000 |
| Official 3136 | 1,000 | 2,000 | 1,000 | 1,000 |
| Official 3151 | 1,000 | 2,000 | 1,000 | 1,000 |
| 3151 with the unchanged Samsung hotfix | 1,000 | 0 | 0 | 1,000 |
| Proposed 3151 hotfix with null-safe logging | 1,000 | 0 | 0 | 1,000 |

Controls passed for ordinary successful lookups, another package name, another method name, unrelated exception types and nonexact messages. The original exception object was preserved. As in the historical patch, the logger safety net matches only exception class/message and is not itself restricted to a method name; the callback bypass is restricted to the exact method name and first argument.

A separate `log((Throwable) null)` control was accepted by all official versions, threw `NullPointerException` with the historical hotfix and was accepted by the proposed null-safe logger. The proposal keeps the original Shared-UID matching policy. See [the full audit](AUDIT_2026-10-24.md).

This reproduces the Java log-generation path under the specified callback behavior. It does not reproduce Samsung's actual callback mix, Android/ART injection, KernelSU soft restart, CPU load or heating. The on-device manifestation in the current official build remains unverified.

## Other local checks

- The existing Samsung patch applies unchanged to 3151 and produces exactly 25 added lines in the same two Java files.
- The proposed script adds one further null check, for 26 source lines added. A missing second anchor leaves both files unchanged; the original script left the first file modified in that failure case.
- `git diff --check` passes for the patched upstream source.
- Official `tests/run-native-regressions.sh` passes under Ubuntu/WSL with Clang and address/undefined-behavior sanitizers.
- Official `tests/run-daemon-regressions.sh` passes; its mount operation is mocked by the upstream test and does not mount anything on the host.
- The GPL-3.0 license matches the current pinned upstream byte for byte.

A complete modified Android build was not run locally. The exact pinned NDK `29.0.13113456` is not present in the inspected Windows SDK; no SDK/NDK installation was performed for this review. The proposed workflow runs the upstream host tests and full build before making a CI artifact available.
